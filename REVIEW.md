## Architectural & Security Issues Copilot Introduced That Required Human Judgment

1. **Unenforced tenant/team boundary (Finding #1).** This is the most serious issue in the file, and it's also the hardest for an AI tool to catch on its own, because the code isn't obviously broken — the model has clean tenant scoping everywhere else, and the gap is disclosed only in a one-line comment that reads as a note-to-self rather than a live vulnerability. Catching it requires knowing the business rule that a team must belong to exactly one organisation and that this relationship has to be enforced at write-time, not assumed — that's domain knowledge, not something inferable from syntax. This is especially risky here because the Notification & Audit service I'm about to build will trust whatever tenant_id is stored on a project; if that value can be attached to the wrong organisation at creation time, every downstream audit and notification record built on top of it inherits the same corruption.

2. **Unreliable audit trail (Finding #3).** The code superficially looks like it's already audit-aware — every function calls an audit hook — which makes it easy to assume compliance is handled. In reality, the emission is fire-and-forget, has no error handling, and silently degrades to a log line if the queue isn't configured. This is a genuinely hard failure mode for an AI tool to flag because the code runs successfully and would likely pass a naive test suite; the gap only becomes visible during an actual incident, when someone goes looking for an audit record that was never durably written. Since the entire purpose of the service I'm building next is to provide a compliance-grade, queryable audit history, this Project Service can't be trusted as an upstream source until this is fixed.
